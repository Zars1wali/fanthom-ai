# Rebuild Fathom (AI Meeting Notetaker): Implementation Plan

> Audience: an AI coding agent + the human operator.
> Goal: ship a **deployed, seeded, polished** meeting-notetaker product in well under 24h, with `.agent-logs/` committed, a public repo, and a 5-minute walkthrough.

---

## 0. Read this first

### 0.1 What is judged
1. **Speed**: how much *working* product exists, and how fast.
2. **Product judgement**: what was built first, what was deliberately left out (and said out loud).
3. **UX/UI**: is it actually good to use?

So: a small number of flows that are **excellent and complete** beats a wide shallow clone. Everything must work on the live link, with seeded data, for a stranger who isn't signed in.

### 0.2 Who does what (agents cannot do everything)

| Human operator (you) | AI agent |
|---|---|
| Do the **8x agent capture setup** and confirm the capture test passes **before any code** | Everything in code, config, seed data, docs |
| Sign up to fathom.video (free plan), connect a calendar, record a real 2-minute self-call, take screenshots | Turn your notes/screenshots into a written "Product Teardown" (`docs/teardown.md`) |
| Provide API keys (Anthropic, DB, optional Deepgram/Google) | Wire env vars, never commit secrets |
| Deploy approval, DNS/domain if any | Deploy config, CI, smoke tests |
| Record the walkthrough (camera ON, <5 min) | Write the walkthrough script (`docs/walkthrough-script.md`) |

### 0.3 Hard gates (do not skip)
- [ ] **Gate 1**: Capture setup done at https://8x-internal.com/p/8x-agent-capture-setup and the **capture test passes**. No product code before this.
- [ ] **Gate 2**: `.agent-logs/` exists in the repo and is committed **incrementally** (every phase, not one lump at the end).
- [ ] **Gate 3**: Live URL opens in an incognito window with **no login required** (demo mode).
- [ ] **Gate 4**: Repo is public, contains `.agent-logs/`, README, seed data, no secrets.

### 0.4 Naming and legality
Do **not** copy Fathom's logo, name, copy or assets. Pick your own product name (e.g. "Tidewater", "Recall Notes", "Huddle"). Recreate *behaviours*, not branding.

## 1. Phase A: Understand the product (human-led, ~45–60 min)

Use Fathom properly. Capture screenshots into `docs/research/screens/`. The agent should read your notes and produce `docs/teardown.md`.

### Checklist of flows to walk end to end
1. Sign up on free plan → onboarding steps.
2. Connect Google/Outlook calendar → see upcoming meetings, per-meeting record toggles/settings (which calendars, internal vs external, who to share with).
3. Notetaker joins a real meeting (Zoom/Meet/Teams) → what does the participant see? (bot presence, consent notice, recording indicator).
4. **During the call**: highlight a moment (hotkey/button). Note how it's labelled and where it lands.
5. **After the call**: how long until it's ready; email/notification; meeting page layout.
6. **Playback ↔ transcript sync**: click a line, seek; auto-scroll while playing; speaker names; speed control; skip silence.
7. **AI summary**: sections, template switcher (e.g. general, sales, 1:1, standup…), regenerate, edit.
8. **Action items**: extraction, assignee, checkbox, jump to timestamp, copy/export.
9. **Highlights** list and creating a clip from them.
10. **Search across meetings** (keyword and "ask" style).
11. **Sharing**: share a clip/meeting with someone not on the call (link, permissions, what they see when not logged in).
12. **Big case**: an 8-person, 60-minute call. Observe: transcript length handling, speaker separation, chapters/topics, summary quality, performance/scroll.
13. Settings, integrations, team/library views, free-plan limits.

### Output of Phase A: `docs/teardown.md`
Sections: *What it does well · What's clunky · What's missing for long/multi-person calls · What I will build · What I will fake · What I will skip (and why)*.

## 2. Product decisions (pre-made, so the agent doesn't dither)

### 2.1 Positioning
"Fathom, but built for the **long, many-person call**": chaptered, speaker-aware, searchable, with summaries that don't fall apart at 60 minutes.

### 2.2 Scope: build order

**P0: must ship (core loop)**
1. **Meetings library** (seeded, 12–15 meetings): list with title, date, duration, attendees, summary snippet, status, filters (date, attendee, has action items).
2. **Meeting detail page**: player + synced transcript + AI summary + action items + highlights in one screen.
3. **Playback ↔ transcript sync**: click-to-seek, auto-follow, speaker colours, speed control.
4. **AI summary with template switcher** (≥4 templates: General, Sales discovery, 1:1, Standup/Project sync) generated by an LLM, cached per (meeting, template).
5. **Action items**: extracted, assignee + timestamp + done toggle, jump-to-moment.
6. **Highlights**: add at any timestamp (button + keyboard `H`), with optional note; appears in the list and on the timeline.
7. **Global search** across all meetings: transcript + summaries + action items; results show meeting, speaker, timestamp, snippet, click → deep-link to that moment. `⌘K` palette.
8. **Share a clip**: pick start/end (from highlight or range) → public link `/s/:token` viewable **without login** (clip player + transcript excerpt + summary snippet, revocable).
9. **The 8-person / 60-minute meeting**: flagship seeded meeting (see §6) with chapters, speaker talk-time, per-speaker filter, virtualised transcript, hierarchical summary.
10. **Demo mode auth**: "Try the demo" button → seeded workspace. No login wall.

**P1: high-value, do if P0 is solid**
11. **Live-meeting simulation (stubbed capture layer)**: "Join a meeting" → paste link → a simulated notetaker "joins", shows recording state, streams a scripted transcript live, lets you press *Highlight* mid-call, and on "end" produces a real meeting via the same pipeline.
12. **Calendar connect**: real Google Calendar OAuth (read-only) **or** stub with seeded upcoming events + per-event "Record" toggle. Pick one (see §7).
13. **Ask the meeting** (chat over one transcript, answers with timestamp citations) and **Ask across meetings**.
14. **Upload audio/transcript** → transcribe (Deepgram/AssemblyAI) → same pipeline (proves it's not fake end to end).

**P2: only if time remains**
15. Follow-up email draft, CRM sync stub, weekly digest, edit summary inline, dark mode, keyboard shortcut cheat-sheet.

**Explicitly OUT (say this in the walkthrough)**
Real meeting bot (Zoom/Meet/Teams), billing, team admin/roles/SSO, CRM integrations, mobile apps, real-time coaching, enterprise compliance. Rationale: capture is a solved commodity (Recall.ai etc.); value is in what happens *after* capture.

### 2.3 What is honest-stubbed
- **Capture layer**: stubbed. Say so in README + walkthrough. Architecture leaves a clean `CaptureProvider` interface so a real provider (Recall.ai) could drop in.
- **Audio**: seeded meetings use generated multi-voice TTS audio (or one looping neutral audio file) behind a `Player` abstraction; if no audio exists the player uses a **synthetic clock** so sync/scrub/highlights still work.

## 4. Architecture

```
                    ┌──────────────────────────────┐
                    │        Next.js (Vercel)       │
Browser  ───────►   │  App Router UI (RSC + client) │
 (public demo)      │  /api/* route handlers        │
                    └───────┬───────────┬──────────┘
                            │           │
                  ┌─────────▼───┐   ┌───▼────────────┐
                  │  Postgres   │   │  Blob storage   │
                  │ (Neon)      │   │  audio / clips  │
                  └─────▲───────┘   └────────────────┘
                        │
        ┌───────────────┴─────────────────┐
        │        Processing pipeline       │
        │ capture → transcript → normalise │
        │ → chapters → summary(template)   │
        │ → action items → index (FTS/vec) │
        └───────▲───────────────────────────┘
                │
   ┌────────────┴─────────────┐
   │ CaptureProvider interface │
   │  • SimulatedProvider (default, scripted)
   │  • UploadProvider (audio → Deepgram)
   │  • RecallProvider (future, not built)
   └───────────────────────────┘
```

### 4.1 Pipeline stages (each idempotent, retryable, status tracked)
1. **Ingest**: raw transcript segments `{speaker, start_ms, end_ms, text}`.
2. **Normalise**: merge same-speaker adjacent turns (<1.5s gap), assign speaker colours, compute talk-time.
3. **Chapter**: detect topic boundaries (LLM over windowed chunks or embeddings/TextTiling) → titles + time ranges.
4. **Summarise (hierarchical / map-reduce)**: summarise each chapter → combine into a template-shaped summary. This is what makes 60-min/8-person calls work.
5. **Action items**: extract per chapter with `{text, assignee, due?, timestamp_ms, source_segment_id}`, dedupe on merge.
6. **Index**: populate `tsvector` columns; (optional) embeddings.
7. **Ready**: status → `ready`, UI updates.

### 4.2 Summary templates
Stored as data (`templates` table or `lib/templates.ts`): `{id, name, description, sections[{key,title,instruction}]}`. Summary generation takes the **chapter summaries** (cheap) and the template → structured JSON → rendered. Cache in `summaries(meeting_id, template_id)`. Switching template is instant if cached, else streams.

### 4.3 LLM rules
- Always request JSON matching a Zod schema; validate; retry once on failure.
- Every claim in a summary/action item should carry a `timestamp_ms` (or segment IDs) so the UI can deep-link. **Timestamps are the product.**
- Cap context: never send a whole 60-min transcript to one call; use chapter chunks.
- Cache aggressively; log token usage; add a `SEED_MODE=precomputed` so seed data ships with **pre-generated** summaries (deploy doesn't depend on live LLM calls for the demo to look great).
- Graceful degradation: if the LLM key is missing/down, show precomputed content and disable "Regenerate" with a tooltip.

### 4.4 Data model (Drizzle sketch)

```
workspaces(id, name)
users(id, workspace_id, name, email, avatar_color)
meetings(id, workspace_id, title, platform[zoom|meet|teams], started_at, duration_ms,
         status[scheduled|recording|processing|ready|failed], audio_url, is_seed bool,
         organizer_id, summary_ready bool)
participants(id, meeting_id, name, email?, is_external bool, talk_ms, color)
segments(id, meeting_id, participant_id, start_ms, end_ms, text, search tsvector)
chapters(id, meeting_id, start_ms, end_ms, title, summary)
templates(id, name, description, sections jsonb)
summaries(id, meeting_id, template_id, content jsonb, model, created_at)
action_items(id, meeting_id, segment_id?, text, assignee_id?, due_date?, timestamp_ms, done bool)
highlights(id, meeting_id, created_by, start_ms, end_ms, note, source[live|manual|ai])
clips(id, meeting_id, token unique, start_ms, end_ms, title, created_by, revoked_at?, view_count)
calendar_events(id, workspace_id, title, starts_at, ends_at, link, platform, record bool, attendees jsonb)
jobs(id, type, payload jsonb, status, attempts, run_at, error)
chat_messages(id, meeting_id?, role, content, citations jsonb)   // P1
```
Indexes: GIN on `segments.search`, GIN on a combined `meeting_search` view/materialised columns for summaries + action items; btree on `(meeting_id, start_ms)`.

### 4.6 Meeting detail UX (make this screen excellent)
- **Left/main**: video-ish player card (audio waveform w/ speaker lanes, highlight markers, chapter ticks), speed control (0.75–2x), ±10s skip, keyboard shortcuts (space, J/K/L, H to highlight).
- **Transcript**: virtualised, speaker-coloured, active line highlighted + auto-follow (with "Jump to live position" pill when user scrolls away), click line = seek, hover = add highlight / copy link-to-moment / create clip, speaker filter chips, in-transcript search.
- **Right panel tabs**: Summary (template dropdown) · Action items · Highlights · Chapters · (Ask, P1).
- **Chapter rail** for long calls; **talk-time bar** per speaker.
- Every summary bullet & action item has a timestamp chip → seeks the player.

## 5. Handling the "8-person, 60-minute" case (the flagship)

Explicit requirements:
- ≥600 transcript segments, 8 named speakers with realistic uneven talk-time, some interruptions/overlaps, 6–10 chapters.
- Transcript virtualised (60fps scroll), no layout shift on active-line change.
- Speaker filter + "who said what about X" via search facets.
- Hierarchical summarisation (§4.1) with **per-chapter** summaries plus overall summary.
- Action items grouped by **assignee** with dedupe.
- Talk-time chart + participation summary.
- Player timeline shows chapters and highlights.
- Loading states: skeletons, streaming summary.

## 6. Seed data (non-negotiable)

Create `scripts/seed/` (deterministic, committed, re-runnable: `pnpm db:seed`).

1. **Generate** realistic transcripts with Claude via `scripts/generate-seed.ts` **once**, commit the JSON output to `seed/data/*.json` (so the seed doesn't need an API key).
2. **12–15 meetings** across kinds: sales discovery (external), customer success QBR, 1:1s, weekly standup, product planning, incident postmortem, hiring debrief, board prep, design review, **the 8-person 60-min all-hands/planning meeting**.
3. Spread dates over the last ~6 weeks; a few with `scheduled` future calendar events; one `processing`; one `recording` (for the live look).
4. Pre-generate **all template summaries** for at least the 4 core templates per meeting (or at least the top 5 meetings), action items, chapters, highlights.
5. Seed 3–4 **shared clips** with stable tokens so `/s/demo-clip-1` works.
6. Seed a realistic team (8–10 named users with colours).
7. Optional audio: generate multi-voice TTS clips (or use a single royalty-free loop) placed in `/public/seed-audio/`. If absent, synthetic-clock player.
8. Search must return meaningful results for demo queries (e.g. "pricing", "Q4 roadmap", "security review", "churn"). Bake these words into transcripts deliberately.

## 9. UX/UI quality bar

- Clean, dense-but-calm productivity UI; one accent colour; consistent 4/8px spacing; Inter/Geist font.
- Fast: route transitions instant (RSC + prefetch), no spinners over 300ms without skeletons.
- Empty/loading/error states designed for every list and panel.
- Keyboard-first: `⌘K`, `/` focus search, `H` highlight, `J/K/L` player, `?` shortcuts.
- Responsive to tablet; usable on mobile for the public clip page especially.
- Accessible: focus rings, aria labels, contrast AA, reduced-motion respected.
- Micro-details that sell it: timestamp chips, active-line highlight, waveform markers, toast on highlight ("Saved at 12:41"), copy-link-to-moment.

## 14. Working rules for the agent

1. Never start coding before Gate 1 passes. Commit `.agent-logs/` at the end of each phase.
2. Deploy early; keep `main` always deployable.
3. Prefer the default stack; log deviations.
4. Small commits, clear messages (`feat(search): ...`).
5. After each phase, actually run the app and verify in a browser (Playwright screenshot) before moving on.
6. Do not spend time on: billing, roles, SSO, real bots, integrations beyond P1 stubs.
7. When blocked on something only the human can do (keys, sign-up, screenshots, recording), stop and ask with an exact, minimal request.
8. Be honest in README about what's stubbed.
